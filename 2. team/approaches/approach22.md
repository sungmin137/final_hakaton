# 접근 22 — v7 + class_scale(HNSC/STES 고정, 나머지 24개 재계산) + 혜림님 라우팅 + 쌍둥이 규칙

## 개요
approach11(v19~v21)에서 발견한 문제에서 출발함: 팀이 계속 재사용해온 고정 class_scale 파일(`6. experiments/2026-09-09_v4_xgb_cs/class_scales_recovered.json`, **2026-09-09에 v7 이전의 다른 모델(v4_xgb_grp)로 딱 한 번 계산된 값**)을 v7 자신의 정직 CV OOF로 다시 계산하면 CV가 크게(+0.0143) 오름. 하지만 재계산본은 STES 배율이 1.0(억제 없음)이 되면서 실제 test 추론 시 STES 예측비율이 23.3%까지 치솟는 위험이 발견됨(approach11.md v21).

이걸 보완하는 절충안(STES만 **3차(성민님) 복원 배율 값**으로 고정)을 검토하던 중, **혜림님의 HNSC/STES 라우터(approach19)가 이 3차(성민님) 복원 배율 파일의 "HNSC=0.7, STES=0.5" 값을 전제로 검증(CV+LB 0.44235)됐다는 걸 확인** — HNSC 배율도 재계산하면 0.7→1.5로 크게 바뀌어 라우터의 개입 조건(메인 예측이 HNSC/STES일 때만 작동) 자체가 달라짐. 그래서 **HNSC/STES 둘 다 3차(성민님) 복원 배율 값으로 고정하고, 나머지 24개 클래스만 v7 전용으로 재계산**하는 걸로 최종 설계를 수정해 실제 제출까지 진행함.

코드: `4. src/submissions_source/approach22_v1_20260912_2357.py` — 이 스크립트 하나가 기본본(`approach22_v1_20260912_2357.csv`)과 쌍둥이 규칙 적용본(`approach22_v1_20260912_2357_twin_rule.csv`) 둘 다 만듦(팀 공통 패턴: 쌍둥이 규칙 적용 전/후를 항상 같이 저장). 두 파일은 메인모델·배율·라우터 판정이 완전히 동일하고 twin_rule 적용 여부만 다름.

**중간 산출물 — `5. submissions/pending_v7refit_hnscstes_pinned_20260912.csv`(+`_twin_rule`)**: approach22와 동일한 설정(HNSC/STES 3차 복원 배율 고정 + 나머지 24개 v7 재계산 + 라우팅 + 쌍둥이 규칙)으로, approach22 스크립트를 정식으로 만들기 전에 **터미널에서 즉석으로 재현·검증하며 만든 결과물**임. 대응하는 `.py` 스크립트는 따로 안 남겼고(파일명에 "pending" 접두사가 그 뜻), 내용은 approach22와 동일하므로 **approach22가 이걸 정식으로 대체함**. LB 제출은 안 됨.

## 결론

**1) class_scale을 v7 전용으로 재계산하는 방향은 실제 LB로 재차 폐기됨.**
approach22 기본본(쌍둥이 규칙 없이도 v7의 0.4377보다 −0.0035 낮음)과 approach22 twin_rule본(쌍둥이 규칙을 넣어도 혜림님 13차보다 −0.0034 낮음) 둘 다, "나머지 24개 클래스 배율을 v7 전용으로 재계산"이 실제 LB에서는 도움이 안 된다는 걸 보여줌. train CV로는 +0.0143 개선으로 보였던 것과 정반대 방향 — 이 프로젝트의 "CV는 LB를 예측하지 못한다"는 원칙이 이번에도 재확인됨. **결론: 3차(성민님) 복원 배율(26개 전부)을 그대로 쓰는 게 낫다.**

**2) twin_rule 단독 효과가 이 프로젝트에서 처음으로 격리 측정됨.**
approach22 기본본과 twin_rule본은 메인모델·배율·라우터 판정까지 완전히 동일하고 twin_rule 적용 여부만 다른 쌍이라, 다른 변수 없이 순수하게 비교 가능:
```
twin_rule 단독 효과 = 0.438953(twin_rule본) − 0.434171(기본본) = +0.00478
```
지금까지 모든 제출은 twin_rule이 라우팅 등 다른 변경과 항상 같이 켜진 채로만 나가서(예: 혜림님 13차, approach11.md의 "13차 상승분 행 단위 분해" 참고) 순수 효과 분리가 불가능했는데, 이번이 처음으로 다른 변수 없이 twin_rule만 켜고 끈 실제 LB 비교임. 다만 이 프로젝트에서 "같은 설정도 재실행하면 LB가 ±0.015 정도 흔들린다"는 기록(`5. submissions/README.md`)이 있어, 이 +0.00478도 한 번의 관측치로 절대적 확정값은 아니고 참고용 기준 수치로 취급함.

**3) 이 approach의 방향(class_scale 재계산) 자체는 여기서 종료.** 앞으로 제출은 3차(성민님) 복원 배율 기준으로 진행하고, class_scale 재계산은 재검토하지 않음.
